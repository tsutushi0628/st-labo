## 実装した機能

### GA4計測の導入

公開されているHTMLはpublic/index.htmlとpublic/prototypes/b-grid-story.htmlの2本のみで、この2本を横断検索してGA・gtag・firebaseConfigの記述がゼロであることを確認した。
計測できなかった原因はst-labo.appというドメインの設定ではなく、HTML側に計測用のスクリプトが存在しなかったことにあった。

Firebase側を確認すると、Webアプリ（displayName ST-Lab）とmeasurementId `G-SP6YD1CVD4` が既に発行済みだった。
IDは用意されていたが、サイト側の指定が抜けていたために計測されない状態になっていた。

このmeasurementIdを取得する過程で、認証まわりの制約に何段階かぶつかった。
Firebase CLIでの個人アカウントログインは、リフレッシュトークンが失効しており401 UNAUTHENTICATEDになった。
gcloudのアクティブアカウントは会社アカウントで、st-laboに対してはFirebase Management APIとCloud Resource Manager APIのどちらも403 PERMISSION_DENIED（IAM権限なし）で拒否された。
そこで個人アカウントを`--account`オプションで明示指定したトークンを試すと通り、さらにFirebase系APIでは`x-goog-user-project: st-labo`ヘッダーがないと403 SERVICE_DISABLEDになることもわかった。
この2つを組み合わせて、measurementIdを取得できた。

本番への反映もFirebase CLIでは行えなかった。同じ401にぶつかるためである。
代わりに、Hosting REST API v1beta1を直接叩く経路（バージョンを作成し、ファイルをgzip化してpopulateFilesへ渡し、アップロード後にFINALIZEDへ遷移させてからリリースを作成する手順）を用いた。
この手順は2回実行しており、2回目が現在の本番状態（isHappyEndを先頭に配置し、画像も差し込んだ最終形）に対応する。

### WORKSへのisHappyEnd追加と並び替え

isHappyEnd（本番 is-happy-end.web.app）をWORKS一覧へ新しいカードとして追加し、クリックで開く詳細モーダル用のテンプレートも合わせて用意した。
追加した時点では一覧の後方に置かれていたが、オーナーから「一番新しいので一番上に」という指示を受けて、一覧の先頭（それまで先頭だったtori-lingualより前）へ移動した。
移動後の掲載順は、isHappyEnd、AIとりリンガル、AIバスケスコアリング、下克上オンライン、AI Agent見える君、Wasurenagusa、its-demo-issho、バスケ動画解析の順になっている。

カードに使う画像は、オーナーから提示されたスクリーンショット2枚を参考に、ヘッドレスChromeでisHappyEnd側の2つの画面を撮影して見比べたうえで決めた。
比較したのは一覧トップ（`/list`）と、日替わりで内容が変わる「きょうの一冊」詳細（`/`、結末の分布を示す半円ゲージつき）の2構図で、採用したのは一覧トップである。
判断の根拠は3つある。

キャッチコピー「ハッピーエンドな本、見つかる。」が画面内に写り込んでおり、カード画像だけでサービスの狙いが伝わること。
撮影した縦横比700対500（1.4）が既存カード画像の比率の範囲（1.44から1.86）に近く、他のカードと並べたときに違和感が出にくいこと。
「きょうの一冊」詳細は日替わりでスコア表示が変わる仕様のため、この画面を採用すると特定の日のスコアがカード画像として固定表示され続けてしまうこと。
既存のCSSは`.work-shot`に`aspect-ratio: 16/9`と`object-fit: cover`を指定してカード画像の縦横比差を吸収する作りになっている。

撮影時にはモバイル幅（390px、414px）で画像の右端が見切れる問題が出た。
700×500の指定に加えて`--force-device-scale-factor=2`を指定し、実寸1400×1000で撮影することでこの見切れを解消した。

本番への反映は、GA4計測の導入で用いたHosting REST API経由の手順に同じである。

## 開発中に得た教訓

### 1. 同じ403でも権限不足とプロジェクト未指定は別原因だった

**何が起きたか**：
Firebase Analyticsのメタデータ取得とHosting反映に向けた認証で、複数の認証エラーが層になって現れた。
Firebase CLIの個人アカウントログインはリフレッシュトークン失効で401になり、再ログイン後はgcloudのアクティブアカウントが会社アカウントのままだったため`st-labo`プロジェクトへのアクセスが403 PERMISSION_DENIEDになった。
`--account`で個人アカウントを明示するとこの403は解消したが、続けてFirebase系APIを叩くと`x-goog-user-project`ヘッダーが無いことを原因とする別の403 SERVICE_DISABLEDが発生した。
同じ403という表面症状の裏に、CLIログインセッション・アクティブアカウント・APIが参照するプロジェクトコンテキストという3つの独立した原因が並んでいた。

**再発防止**：
gcloud・Firebase CLI系のエラーはHTTPステータスコードだけで原因を一つに決めつけず、CLIログインセッション・`gcloud auth list`で見えるアクティブアカウント・APIリクエストのプロジェクトコンテキスト（`x-goog-user-project`ヘッダー等）の3層を分けて確認する。
個人・会社の複数アカウントを切り替える環境では、`gcloud`のアクティブアカウントが意図したものと一致しているかを最初に疑う。

**反映先候補**：
`.claude/skills/firebase-howto/SKILL.md`（gcloud・Firebase CLIのマルチアカウント運用知識として追記）

### 2. GA4が動かない原因はドメインでなく発行済みタグの未実装だった

**何が起きたか**：
Firebase Analyticsの計測値が取れない原因として、最初はドメイン設定を疑った。
実際に調べると、Firebaseコンソール側ではWebアプリの登録とmeasurementId（`G-SP6YD1CVD4`）の発行がすでに完了しており、欠けていたのは公開HTML側のgtag/GAスニペット1行だった。
「未設定」ではなく「設定済みの資源がコード側から一度も呼ばれていない」状態だった。

**再発防止**：

「用意されている」と「コードから指定されている」は別の状態であり、後者を確認しないまま前者を理由に外部要因を疑うと調査が遠回りになる。

### 6. HostingのheadersグロブがルートURLにマッチしなかった

**何が起きたか**：
`firebase.json`のHosting `headers`で`"source": "**/*.html"`を指定していたが、このグロブはルートURL（`/`）へのリクエストにマッチしない。
ルートは暗黙的に`index.html`へリライトされるが、リクエストパス自体はファイル名を持たないため、ファイル名ベースのグロブでは拾えない。
結果として、ルートURLの応答にだけX-Frame-Options等のセキュリティヘッダーが付かない状態になっている。

**再発防止**：
Firebase Hostingの`headers`をファイル名グロブ（`**/*.html`等）で指定するときは、それがルートパス`/`にはマッチしない前提を持つ。
ルートにも同じヘッダーを効かせたいなら、`source`にルート自体を含む指定（`/`の個別追加や`**`相当の包括パターン）を別に用意する。

**反映先候補**：
`.claude/skills/firebase-howto/SKILL.md`（Hosting `headers`設定の注意点として追記）

### 7. Codex生成のworklogが個人パスを含みコミットガードに引っかかった

**何が起きたか**：
Codex委譲経路が生成する`docs/findings/codex-worklog.md`は、最終メッセージ冒頭に個人ホーム配下の絶対パスを含む形式で記録される。
このファイルをコミットしようとすると、個人ホームパスをハードブロックするシークレットガードに引っかかるため、未追跡のまま残置せざるを得なかった。

**再発防止**：
fusion経由でCodexに委譲する運用を使うプロジェクトでは、`codex-worklog.md`が個人パスを含みうる前提を持つ。
コミット対象に含めるかどうかを、`.gitignore`登録または出力側でのパス相対化によって事前に決めておく。

**反映先候補**：
`.claude/fusion/codex-task--run--with-rules-and-worklog.sh`（worklog出力のパス相対化、または`.gitignore`登録の検討）
